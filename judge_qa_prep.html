1

Tech stack — the basics

The questions every judge opens with, to see if you can even name what you built.

What's the tech stack, top to bottom?

Frontend: Next.js 16 (App Router) + React 19 + TypeScript + Tailwind CSS 4.
Backend: no separate backend service — Next.js Server Actions and Route Handlers run server-side logic directly, talking to Postgres through Drizzle ORM.
Database: PostgreSQL, hosted on Neon (serverless Postgres).
Auth: custom — scrypt password hashing, httpOnly session cookies. No third-party auth provider.
AI: Groq's OpenAI-compatible API, running an open-weights model (gpt-oss-20b).
Deployment: Vercel, auto-deployed from GitHub on push to master.

Say it like thisNext.js and TypeScript on top, Postgres on the bottom, and no separate backend server in between — Server Actions call the database directly, inside one transaction, per request.
Why Next.js instead of a separate frontend + backend (e.g. React + Express)?

Server Actions let a form submit straight into server-side, transactional database code with no hand-written API route, no client-side fetch boilerplate, and no separate deployment to keep in sync. For a system where every write has to go through one authorization+transaction wrapper, having the framework do that plumbing for free was worth it more than framework flexibility.

Say it like thisIt collapses the API layer — a form submit is a direct, typed, server-side function call inside a transaction. Fewer moving parts means fewer places for the authorization check to be accidentally skipped.
Why Postgres and not MongoDB / Firebase / a NoSQL store?

The entire idea depends on relational joins staying cheap and correct: revenue rows and cost rows share a batch_id foreign key, and per-batch profit is a GROUP BY over that join. That's Postgres's home turf. It also gave two features for free that a NoSQL store doesn't have natively: row-level security (real per-role data isolation enforced by the database, not the app) and rules/constraints (the append-only ledger is enforced by a database rule, not a promise in application code).

Say it like thisThe core idea — batch_id ties revenue and cost together — is a join. A relational database is the only sane place to make that join both fast and provably correct.
What is Drizzle ORM, and why use it?

A lightweight TypeScript ORM. It's used here mostly for typed query building and schema types — the actual schema was hand-written in raw SQL (db/schema.sql) and Drizzle introspects it, rather than Drizzle owning the schema. That was deliberate: the schema needed real Postgres features (RLS policies, a rule blocking UPDATE/DELETE, custom enum types) that are easier to write directly in SQL than to fight an ORM's migration DSL for.

Why Groq instead of OpenAI or Anthropic's API for the AI features?

Cost and speed for a demo context — Groq's hosted inference is fast and has a generous free tier, which matters when you need the AI consultant to answer live, in front of judges, without a billing surprise. The model is an open-weights reasoning model (gpt-oss-20b) served through an OpenAI-compatible endpoint, so the integration code is portable if the model choice ever needs to change.

Say it like thisGroq gives us fast, cheap inference for a live demo — and because the AI's actual safety boundary is a database-level read-only grant, not the model provider, swapping models wouldn't change the security story at all.

How it actually works

One level past "what did you use" — the actual mechanics of a request.

Walk me through what happens when someone submits a form — say, "record a payment."

The form calls a Server Action, which calls one shared function: authorizedTransaction(permission, fn). That function (1) checks the logged-in user actually has that permission, (2) opens a single Postgres transaction, (3) runs SET LOCAL ROLE continuum_staff to downgrade the database connection to a restricted role for the rest of that transaction, (4) sets two session variables — app.user_role and app.party_id — that Postgres's row-level security policies read, then (5) runs the actual insert inside that same transaction. So every write is authorized twice: once in application code, once by the database itself.

export async function authorizedTransaction(permission, fn) {
  const user = await requireUser(permission);
  return db.transaction(async (tx) => {
    await tx.execute(sql`set local role continuum_staff`);
    await tx.execute(sql`select set_config('app.user_role', ${user.role}, true),
                                 set_config('app.party_id', ${user.partyId}, true)`);
    return fn(tx, user);
  });
}
Say it like thisEvery write goes through one funnel function that checks permission, opens a transaction, and downgrades the database connection to a restricted role before the actual insert runs — so authorization is enforced twice, by two different systems.
What stops a double-click from creating two payments, or a network retry duplicating a write?

Idempotency, built at the request level, not just disabling a button in the UI. Every mutating form generates a random UUID client-side once (crypto.randomUUID(), held in a useRef so it survives re-renders but not a real new submission) and sends it as a requestId. Server-side, before doing anything else, the code takes a Postgres advisory lock keyed on hashtextextended(user_id + requestId) — so two near-simultaneous copies of the exact same request serialize instead of racing — then checks an operation_request table keyed on (user_id, request_id). If that row already exists, it returns the previously stored result instead of re-running the write.

Say it like thisA retry is safe by construction — the same request ID always resolves to the same stored result, because I check a request table before doing the write, guarded by a database advisory lock so two retries can't race each other.
How is per-batch profit actually calculated? Walk through the math.

It's a Postgres view, batch_pnl — not code I wrote in TypeScript. Every revenue row (invoice_line) and every cost row (expense, trainer_payment) carries a batch_id foreign key. The view groups by that column, sums revenue on one side and cost on the other, and subtracts. The dashboard just SELECTs from that view — it never re-derives profit in application code, which means the number on screen and the number in the database can never disagree.

net_profit =
  SUM(invoice_line.amount - discount)
  - SUM(expense.amount)
  - SUM(trainer_payment.amount)
  -- grouped by batch_id
Say it like thisProfit isn't computed in my app — it's a GROUP BY in a Postgres view. The dashboard just reads it. That's the whole reason "per-batch net profit" can be a live number instead of a month-end spreadsheet.
What is the "event log" / ledger, concretely? Is Continuum event-sourced?

No — this is worth being precise about if asked directly. Continuum is a normal relational, transactional system with an append-only audit log alongside it, not an event-sourced system where state is rebuilt by replaying events. ledger_event is that audit table — every write in the system also inserts one row here: event type, entity affected, which batch it belongs to, and a signed amount if money moved. It's genuinely append-only: a Postgres RULE on that table turns UPDATE and DELETE into no-ops at the database level. Current business state comes straight from the operational tables (invoice, payment, batch...), never from replaying the ledger.

Historical / "as-of" P&L works the same way — batch_pnl_asof(date) filters the operational financial records by their own effective timestamps, on or before the requested date. It is not replaying the event log to reconstruct a past state.

Say it like thisIt's relational with an append-only audit log, not event-sourced — current state lives in the operational tables. The ledger gives me audit trail and traceability; historical P&L is a query filtered by effective date, not a replay.
How does the AI consultant turn a question into SQL, and get an answer back?

The user's question goes to Groq with a system prompt describing the three whitelisted views' schemas. The model returns SQL. Before that SQL ever runs, it goes through a validator (sqlGuard.ts) that checks it's read-only, touches only the three whitelisted views, and uses only a small allowlist of safe functions (SUM, COUNT, AVG, MIN, MAX, ROUND) — plus a second check that runs Postgres's own EXPLAIN on it, which catches anything regex-based rules could miss. Only then does it execute, using a database role that has SELECT on exactly those three views and nothing else, inside a read-only transaction with a statement timeout and a row cap. The UI shows the answer and the SQL that produced it, plus a trace link.

Say it like thisThe model proposes SQL, a validator checks it before it runs, and then it executes under a database role that literally cannot see anything but three read-only views — so even a validator bypass can't leak data, because the database itself is the real boundary.
How does the student assistant know which student it's talking to?

Not from anything typed into the chat — from the session. The logged-in user's party_id is set as a Postgres session variable (app.party_id) inside the transaction, and row-level security policies on enrollment, attendance, invoice, payment filter every query to rows belonging to that party. The assistant also doesn't do free-form SQL like the consultant — it only routes to one of two fixed, parameterless typed tools ("next class," "balance"), each of which runs under that same RLS-scoped connection. The model's only output is one word (SCHEDULE or BALANCE); it never sees or supplies an identity.

Security & data integrity

Where judges probe whether "secure" is a real claim or a slide word.

What is row-level security, exactly, and where is it actually enforced?

RLS is a Postgres feature: a policy attached to a table that filters every row a given database role can see or write, evaluated by Postgres itself — not by application code deciding "don't show this." A trainer's policy on attendance, for example, reads: only rows where the enrollment's batch is taught by this session's trainer (via app.party_id). I verified this two ways: through the normal app UI, and by connecting directly as the restricted role and issuing a raw query that tries to read another trainer's data — it comes back empty, proving the app-layer permission check isn't the only thing stopping it.

create policy attendance_access on attendance for select using (
  exists (select 1 from enrollment e join batch b on b.id = e.batch_id
          where e.id = attendance.enrollment_id
          and b.trainer_id = current_setting('app.party_id')::uuid)
);
Say it like thisRLS is enforced by Postgres, not by my code — I proved it by bypassing my own app layer entirely and querying the database directly as a restricted role. It still refused to return another trainer's data.
How many database roles are there, and why more than one?

Three, each least-privilege for its purpose — separate from the six business roles (management, sales, ops, finance, trainer, student) the app itself has. continuum_ai — read-only, SELECT on exactly 3 views, zero grants on any base table, used only by the consultant. continuum_app — RLS-scoped reads, used by the student assistant. continuum_staff — RLS-scoped writes, used by every authenticated write in the app. None of them can bypass RLS (NOBYPASSRLS). The point of splitting them is that a bug in one feature's code can't accidentally grant it another feature's privileges — the ceiling is set at the database level, per role, not per code path.

Don't conflate these"6 roles" and "3 roles" are both correct answers to different questions — business roles (what a person is) vs. database roles (what a connection can do). Mixing them up mid-answer is the kind of slip a sharp judge will catch.
Passwords — how are they stored, and how does login actually verify one?

scrypt — a memory-hard hashing function, not a fast general-purpose hash like SHA-256 (which would be crackable at scale for passwords). Verification uses timingSafeEqual for the byte comparison, so the comparison time doesn't leak how many bytes matched. And if the email doesn't exist at all, the login code still runs a dummy hash comparison against a fixed value — so a wrong password and a nonexistent account take the same amount of time to reject, which stops someone from timing their way into discovering which emails have accounts. Session tokens themselves are stored server-side only as a SHA-256 hash — the raw token lives only in the browser's httpOnly cookie, so a leaked session table alone can't be replayed as a live session.

Say it like thisEven the failure path is designed — a wrong password and a non-existent account are indistinguishable in both the message and the response time.
What happens with the forgot-password flow, technically?

It validates the email format, rate-limits attempts (both globally and per-email, using Postgres-backed counters), then looks up the account. Whether or not it exists, the response is the identical generic message — "if that email is registered, a new password has been sent" — for the same anti-enumeration reason as login. If it does exist: generate a random temp password, hash it, force must_change=true, invalidate all existing sessions for that user, log a password.reset_requested ledger event, and actually email the temp password via Resend. Next login forces a password change before anything else is accessible.

Honest limitationThe email send happens after the database commit — if delivery fails, it's logged server-side but the user isn't told differently (by design, for anti-enumeration). A production version would want a durable outbox/queue so the write and the send commit atomically.
How do you know the RLS policies and the app-layer permission checks actually agree with each other?

I ran a full authorization matrix: all 6 business roles against every write operation, checked through the normal app, and then the same unauthorized-write attempts repeated with the app-level check removed entirely — calling the database layer directly as if a permission bug existed. Every one was still blocked by RLS. That's the actual point of having two layers: even a bug in my own authorization logic wouldn't expose a real data leak, because the database enforces its own copy of the rule independently.

Is any of this actually verified live, or is it "should work"?

Verified live, deliberately — every number on the dashboard, the per-batch table, and invoice statuses was independently recomputed from raw tables and matched exactly. All 8 seeded accounts were logged into for real, across every route (72 role×route checks total), confirming correct access and correct denial (redirect to /forbidden, or a 401 JSON response for the AI API routes when unauthenticated). Security headers (HSTS, CSP, X-Frame-Options), the HTTPS redirect, and the session cookie flags (httpOnly, secure, sameSite=Lax) were all checked against the live deployed response, not just the code. This session's mobile-responsive fixes were also verified the same way — real Playwright screenshots at 375px/390px/768px/1280px against the live production build, not just "the build compiled."

Hard questions — architecture & trade-offs

These test judgment, not recall. It's fine to reason out loud here.

Why an append-only audit log at all, if you're not event-sourced? Why not just normal tables with an updated_at column?

Because two of the brief's actual requirements are hard to fake with plain mutable rows: a real audit trail, and traceability from a lead to its financial outcome. An updated_at column tells you a row changed, not what it was before, who changed it, or why. The ledger_event table gives an explicit, provably-unmodifiable record of every meaningful action — enforced by a Postgres rule, not a convention. The cost is real: every write also has to emit an event. For a system whose entire pitch is traceability, that complexity buys the actual differentiator, not gold-plating.

Say it like thisThe audit log isn't there to rebuild state — it's there so "who changed what, when" is a real, tamper-proof answer instead of a promise.
Why enforce RLS at the database level instead of just checking permissions in your Server Actions? Isn't that redundant?

It's redundant on purpose — that's called defence-in-depth. App-layer checks are code I wrote, and code has bugs; I've already found and fixed two RLS policy bugs during testing that would have leaked data (documented in the commit history, not hidden). If the only thing stopping a student from reading another student's attendance is an if statement in a Server Action, one missed check anywhere in the codebase is a real leak. With RLS, that same mistake still gets caught by the database, because the restricted role physically cannot see rows outside its policy — independent of what my application code did or didn't check.

The AI consultant generates SQL from natural language. How do you actually know it can't leak data or run something destructive?

Because the safety boundary isn't the prompt or the model's good behavior — it's the database grant. continuum_ai has SELECT on exactly three views and zero grants on any base table or any other view. Even if the model were adversarially prompted to generate DROP TABLE payment or SELECT * FROM app_user, the connection it runs under would reject it at the database permission layer before Postgres even considers executing it. The SQL validator in front of that is real, but I explicitly documented it in the code as "defence-in-depth, not the actual boundary" — because I don't trust a regex to catch every SQL injection shape, but I do trust a Postgres grant, because that's the same mechanism every real production database's security rests on.

Say it like thisI don't trust the AI to behave — I trust the database to enforce a grant it can't talk its way around. The validator is a nice-to-have in front of a hard boundary, not the boundary itself.
What's the actual security/consistency trade-off in the refund design? Why not just delete or edit the original payment?

Because the append-only rule means you literally can't edit or delete a payment row — and even if you could, that would break the "money in = sum of payment rows" invariant everything else relies on. A refund is instead recorded as a new payment row with a negative amount, and its link back to the original payment lives in the ledger event's payload, not in an overloaded column — I actually started by encoding it into payment.method as a hack and caught that mid-build, because it would have shown garbage strings like refund:abc123 in the finance UI's method column and conflated "how it was paid" with "what it refunds." The server also independently checks a refund can never exceed what was actually collected on that installment, summed from the ledger — not trusted from the client.

Say it like thisA refund is a new ledger-tracked event, not a mutation — because the whole system's invariant is that money rows are never edited, only added, and I caught and fixed a real over-refund bug by making that check happen at the database read, not the form.
How would this scale if you had 10,000 batches and 100,000 ledger events? Where does it break first?

Honestly: the reporting views that aggregate a growing financial history, plus external AI latency, would be the first real bottlenecks — not the React UI. The views (batch_pnl, collections_aging) are plain GROUP BYs, which Postgres indexes and plans well up to real production scale, but the as-of query filtering the whole financial history by effective date would need measured indexes or pre-aggregation at real volume. Rate limiting is currently per-instance Postgres counters, which is fine for a demo but would need a proper distributed store (Redis, etc.) under real concurrent load. I'd call this "production-shaped," not "production-scale" — the patterns are right, the scale headroom hasn't been load-tested past a few hundred batches.

Say it like thisThe patterns are the right ones for scale — but I haven't load-tested past a demo-sized dataset, and I'd say that honestly rather than claim numbers I haven't verified.
Why did you build this "with AI"? Doesn't that mean you don't really understand it?

I used AI as a pair-programmer, the same way I'd use a very fast, very well-read colleague — it wrote a lot of first-draft code and helped me move faster, but every architectural decision was mine: choosing the batch as the shared profit key, choosing to split into three database roles instead of one, catching and fixing the refund-encoding mistake myself mid-build, catching a real CSS layout bug in the mobile redesign by actually screenshotting it rather than trusting "the build passed." And I didn't just accept what was generated — I adversarially tested the security boundaries myself: connecting as the restricted database roles directly, trying to read data across role boundaries, checking the actual live HTTP responses and headers. If I didn't understand it, I couldn't have found or explained any of the bugs I found and fixed.

Say it like thisAI wrote code faster than I could type it — but I made the architecture calls, and I broke it myself to prove the security boundaries actually hold, not just to trust that they would.

"Why didn't you just use—"

Comparison questions. Answer briefly, then pivot back to your differentiator.

Why not just use Zoho / Salesforce / an off-the-shelf CRM?

Those are excellent at the CRM half — pipeline, contacts, activities. None of them natively join a lead to the cost side of a batch (trainer fees, venue, materials) in the same record set. That join always happens in a spreadsheet at month-end, done by a human. That's the exact gap PS-04 is scoring.

Why not Arlo, which is actually a training-management system?

Arlo genuinely has deeper scheduling and a public course-booking site than we do — and we scoped that out on purpose (it's explicitly out-of-scope in our own project brief). But Arlo hands off accounting to Xero — it doesn't own per-batch profit inside its own record set either. We trade Arlo's scheduling depth for owning the full enquiry-to-margin chain natively.

Why not Odoo, since it's a full ERP with a training module?

Odoo can technically build this — it's a generic ERP framework. But "per-batch net profit as a first-class, pre-built number" isn't something it ships with; you'd configure and build it yourself, module by module. We built the batch-as-profit-centre model as the actual foundation of the schema, not a customization on top of a generic one.

Ready for a controlled pilot after the checks I've already run — build, lint, typecheck, integration tests, RLS reconciliation, a full role×route matrix, dependency audits, live security headers. How the mobile-responsive pass was actually built

Design tooling, tech, and the real bug that got caught and fixed — not "we added some media queries."

What's the mobile tech stack — did you add any new libraries?

No new runtime libraries — it's the same stack (Next.js, React, Tailwind CSS) doing more with what was already there. Two small new files: NavIcon.tsx, a hand-drawn inline SVG icon set (dashboard, CRM, training, finance, etc.) instead of pulling in an icon font or library like Material Symbols or Font Awesome — keeps the bundle lean and matches the app's existing dependency-light style. And MobileNav.tsx, a new client component for the phone-only navigation chrome. Everything else is Tailwind responsive classes (sm:, md:, lg: breakpoints) and plain CSS added to the existing globals.css.

Say it like thisZero new dependencies — it's Tailwind's existing breakpoint system plus about 250 lines of new component code, not a rewrite or a new framework.
How did you actually design the mobile screens before coding them?

Used Google's Stitch (an AI UI-design tool) to generate mobile-first mockups for all 13 screens in the app, seeded with a written spec describing the real component paths, the existing navy/teal design tokens, and three target resolutions (375px iPhone SE, 390px iPhone 12/13/14, 768px iPad portrait). Stitch's own output included a written component-mapping spec — which existing file each redesigned screen maps to, and the exact Tailwind pattern to use for the table→card conversion. That spec was then implemented by hand, directly in the real Next.js components — not pasted in wholesale, translated deliberately so business logic, permissions and data shapes were never touched, only layout.

Say it like thisStitch gave me a mobile design system and a component map; I did the actual implementation myself, verifying each change against the real app rather than trusting a generated mockup.
Walk me through the two biggest structural changes.

1. Navigation. Below md (768px), the old sidebar degraded into an awkward 2-column link grid. Replaced with three real mobile patterns in MobileNav.tsx: a fixed top bar (hamburger, breadcrumb, account), a bottom tab bar showing the signed-in role's top 4 workspaces, and a slide-in drawer listing every workspace that role can reach. Both the desktop sidebar and the new mobile nav read from one shared navItemsFor(role) function in SidebarNav.tsx, so there's one source of truth for "what can this role see," not two lists that can drift apart.

2. Tables → cards. DataTable.tsx now renders two layouts from one component: below 640px, each row becomes a stacked card (title, optional status pill, label/value grid); at 640px and up, the original <table> renders unchanged. Fully backward compatible — every existing <DataTable columns rows/> call needed zero changes, since the new title/status column indices are optional props with sane defaults.

Say it like thisNobody should have to horizontally scroll through a table mid-demo on a judge's phone — every list in the app now has a real mobile layout, not a shrunk desktop one.
Did anything actually break, and how did you catch it?

Yes — a real bug, and it's worth telling this story precisely because it demonstrates the verification discipline, not just the fix. After compacting the login and forgot-password pages' dark brand panel for mobile, I initially trusted a clean npm run build as proof it worked. It didn't — there was a large dead gap between the banner and the actual sign-in form. I only caught it by actually installing Playwright (python -m playwright, no special MCP tool required — I'd assumed I didn't have this capability earlier in the session and was wrong) and screenshotting the real rendered page at phone width. Two compounding CSS Grid issues: the page's outer <main> was unconditionally grid, and an implicit single-column grid row stretches to fill its container's full height by default — so both page sections were stretching to fill min-h-screen even on a phone, where there's no split-screen layout to stretch for. Fixed by making the grid itself conditional on lg: — below that breakpoint it's plain block flow, so each section is exactly as tall as its own content.

<!-- before: always a stretching grid row, even on phones -->
<main className="grid min-h-screen lg:grid-cols-2">

<!-- after: grid (and the stretch behavior) only applies from lg up -->
<main className="lg:grid lg:min-h-screen lg:grid-cols-2">
Why this is worth telling, not hidingIt's a better answer than "everything worked first try" — it shows the actual verification loop: build passing is not proof of correct layout, a real screenshot at the real breakpoint is.
Say it like thisMy first fix looked done because the build passed — it wasn't, and I only found that by actually rendering the page and looking at it. That's the whole reason I verify with real screenshots now, not just a green build.
What specific accessibility/touch details did you handle?

44px minimum tap targets on every interactive element — applied globally via CSS (.primary buttons and every <details><summary> collapsible-form header get min-height rules in globals.css, rather than patched one call site at a time), so the fix applies everywhere at once and can't be missed on a new form later. Submit buttons go full-width on mobile (w-full sm:w-auto). Select dropdowns with long generated labels (e.g. "Acme Corp / ₹40,000 / 2026-09-01") truncate instead of overflowing the viewport. Safe-area insets (env(safe-area-inset-top/bottom)) clear the fixed top bar and bottom tab bar from a phone's notch or home-indicator.

How was this actually verified — locally and live?

Every claim here has a screenshot behind it, not a guess. Locally: a clean production build (rm -rf .next && npm run build) served with npm run start, screenshotted with Playwright at all three target breakpoints plus 1280px desktop, checking both visual layout (no dead gaps, no clipped content) and document.body.scrollWidth against the viewport width (catches horizontal overflow programmatically, not just by eye). Then pushed, waited for the Vercel deployment to report Ready, and re-ran the exact same Playwright check against the live production URL — because a local pass doesn't prove the deployed build behaves the same way.

Say it like thisEvery mobile fix was screenshotted twice — once locally before pushing, once live after deploying — because "it built" and "it deployed" are both necessary and neither is sufficient proof it actually renders right.

Putting it together

How to talk about the problem statement and your solution, in one breath

The problem, in one sentence: PS-04 asks for one platform that runs a training business from first enquiry to net profit — but revenue tracking is easy and profit tracking is where every existing tool quits, because nobody ties a lead to the batch's actual costs in the same system.

The solution, in one sentence: we modeled the batch as the profit centre — every revenue row and every cost row carries the same batch_id, in one relational Postgres schema with an append-only audit log, so per-batch net profit is a live database query instead of a month-end spreadsheet walk.

The proof, in one sentence: it's not a mockup — RLS is enforced by the database and independently verified by bypassing the app layer, the AI is grounded to three read-only views by an actual database grant, and every number on the live dashboard was recomputed from raw tables and matched.

If you remember nothing else: "most teams build a CRM — we built a ledger, and we proved every boundary in it actually holds."
